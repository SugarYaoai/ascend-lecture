1.5 TensorOJ 实战：Add Medium 的 Tile 分块

1.5.1 问题引入：更大数据量带来的片上内存挑战

1 / 3
本节题目链接：TensorOJ Add Medium
计算类型：float32 一维向量逐元素加法
向量加法计算公式
zi = xi + yi,    i ∈ [0, 1048576)
① 任务规模扩大
N = 1,048,576

单次任务数据规模扩大至百万级 float32 元素

② 多核均分负载
16 个 Block

固定启动 16 个 Block，单 Block 需处理 65,536 个元素

③ 核心物理矛盾
单 Block 输入 x, y 与输出 z 无法一次性放入片上 UB

全量驻留需求远超单个 AI Core 片上 SRAM 容量

单核负载与 UB 需求测算
1. 长度 1048576 均分给 16 个 Block
BLOCK_LENGTH = 1048576 / 16 = 65536
2. 同时驻留 x、y、z 三份 float32 缓冲区
3 × 65536 × 4 B = 768 KB

Block 切分仅解决多核并行分工、缩短整体运行时间，无法突破单个 AI Core 内部 UB 的物理容量上限。

硬件约束（UB 物理上限）
单个 AI Core UB 名义容量 256 KB 片上 SRAM 物理上限
全量载入所需 UB 空间 768 KB 达到物理上限的 3 倍
这不是性能较差，而是片上 SRAM 容量硬性不足；若强行静态全量分配，代码会在编译期或运行初期直接失败。
Card 1 · 两级切分分工
  • Block 切分（空间并行）：16 个 Block 分管不同 GM 区间，实现多核并行
  • Tile 切分（时间复用）：单核内用 for 循环复用同一组 UB 空间，分批完成数据
Card 2 · 单 Tile 内存占用
3 × 8192 × 4 B = 96 KB
  • 选定 TILE_LENGTH = 8192（满足 32 B 对齐且留有 UB 余量）
  • 任意时刻仅 96 KB 驻留 UB，取代不可容纳的 768 KB
C++ · 两级切分静态配置 
constexpr uint32_t NUM_BLOCKS = 16;
constexpr uint32_t BLOCK_LENGTH = 65536;
constexpr uint32_t TILE_LENGTH = 8192;
constexpr uint32_t TILE_NUM = BLOCK_LENGTH / TILE_LENGTH;
// 每个 Block 循环 8 次。
每个 Block 通过 TILE_NUM = 8 次循环依次搬入、计算并写回一个 8192 元素的 Tile，稳妥完成全部 65536 个元素。
